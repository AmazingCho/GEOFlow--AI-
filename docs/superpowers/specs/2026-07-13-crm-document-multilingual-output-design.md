# CRM 单据四语言输出设计

## 状态

- 需求状态：已通过 PM 合理性审核
- 设计状态：待用户确认书面规格
- 支持语言：English (`en`)、简体中文 (`zh_CN`)、Русский (`ru`)、Español (`es`)

## 产品目标

让同一份 CRM 单据在不复制数据、不创建语言副本的前提下，输出英文、中文、俄语或西班牙语版本。语言切换只改变系统控制的固定文案和日期展示，不自动翻译或覆盖用户录入的业务内容。

适用单据：

- 报价单
- 形式发票
- 商业发票
- 装箱单
- 合同草稿

适用输出：

- HTML 打印预览
- Chrome 打印
- Download PDF
- Excel 导出
- PDF 视觉回归包

## 现状审计

现有系统已经通过 `crm_quotes.document_language` 保存英文或中文，但实现仍以 `$isZh ? ... : ...` 和局部数组为主，未形成完整词典。

已发现的中文映射缺口包括：

- `Buyer / Customer`
- `Terms & Conditions`
- `BANK ACCOUNT`、`Payment Summary`
- `Note`、`Total Invoice Value`
- `Origin: China`
- 续页标题、页码文本、生成提示
- 部分银行、物流、装箱和签名字段
- 日期仍可能显示英文月份
- Excel 导出仍独立维护中英文判断
- PDF 回归服务重复维护标签数组

打印 URL 当前携带 `language` 参数，但控制器未使用该参数决定输出语言，PDF 下载链接也没有完整继承预览语言。

## 方案比较

### 方案 A：继续扩展 Blade 中的条件判断

把 `$isZh ? ... : ...` 扩展为四语言 `match`。

优点：短期改动直观。

缺点：文案继续散落，容易漏翻译；HTML、PDF、Excel 和回归服务会重复维护；后续新增语言成本高。

结论：不采用。

### 方案 B：统一单据语言目录和显式语言服务

使用四套单据专用语言文件，并由一个显式的单据语言服务统一提供语言白名单、标题、标签、日期格式和回退规则。

优点：单一来源、可测试、与后台界面语言解耦；五种单据和四种输出共用；以后增加语言无需复制模板。

缺点：第一次需要清理现有硬编码。

结论：采用。

### 方案 C：后台可编辑数据库词典

把翻译保存在数据库并提供管理页面。

优点：无需改代码即可修改文案。

缺点：增加治理、权限、误操作和回滚成本；当前仅四种受控语言，没有足够收益。

结论：本阶段不采用。

## 最终设计

### 1. 语言来源

单据保留一个已保存的默认语言。输出时按以下优先级解析：

1. 打印、PDF 或 Excel URL 中合法的 `language` 参数。
2. 单据保存的 `document_language`。
3. 英文 `en`。

URL 临时语言只影响本次输出，不回写数据库。

### 2. 前端交互

编辑单据页面的“单据语言”增加四个选项，用于保存默认语言：

- English
- 简体中文
- Русский
- Español

字段下方显示说明：`仅切换系统标题和标签；产品、客户、条款及银行资料保持录入原文。`

打印预览顶部增加“本次输出语言”选择器，与现有单据类型选择器并列。切换后重新打开相同单据类型和相同记录，只改变 `language` 参数。该控件在打印和 PDF 中隐藏。

PDF 下载与 Excel 导出继承当前预览语言，避免预览为俄语但下载结果回到默认语言。

### 3. 翻译边界

自动切换的内容：

- 单据名称和页面标题
- 买卖双方、商业信息、物流、装箱、汇总、条款、签名等系统字段名
- 表头、续页标题、页码和系统提示
- 银行信息的字段名
- 系统生成的固定说明
- 日期月份和日期顺序

始终保留原文的内容：

- 产品名称、型号、SKU、HS Code
- 产品描述、数量单位
- 客户、联系人、国家、地址和税号
- 卖方公司名称、地址和联系方式
- 银行名称、账户、SWIFT、Bank Code、Branch Code 和银行地址
- 付款、交付、质保、安装、包装及合同自定义条款
- 备注、签名说明和物流值
- 金额、币种代码和数值格式

例如俄语单据可显示 `Банк получателя` 作为字段名，但实际银行名称和账号保持录入内容不变。

### 4. 代码结构

新增单据专用语言目录：

- `lang/en/crm_document.php`
- `lang/zh_CN/crm_document.php`
- `lang/ru/crm_document.php`
- `lang/es/crm_document.php`

新增 `App\Support\GeoFlow\CrmDocumentLocale`，职责限定为：

- 返回受支持语言及管理界面显示名称
- 标准化并验证语言代码
- 按显式语言读取文案，不依赖当前后台会话语言
- 返回五种单据标题
- 提供单据日期格式化
- 缺少键或非法语言时回退英文

控制器、打印模板、Excel 导出和 PDF 回归服务统一使用该支持类。删除重复的 `documentLabels()` 和散落的二元语言判断。

Blade 继续复用现有打印 partial，只接收统一的 `$label`、`$documentTitles`、`$documentLanguage` 和日期格式化结果，不为俄语或西班牙语复制模板。

### 5. 日期与数值

日期按输出语言显示：

- English：`Jul 13, 2026`
- 简体中文：`2026年7月13日`
- Русский：`13 июл. 2026 г.`
- Español：`13 jul 2026`

金额和数量继续沿用现有格式及币种代码，不自动切换为逗号小数或翻译单位，避免商业数字歧义。

### 6. 错误与回退

- 保存非法语言值时返回表单验证错误。
- URL 提供非法语言时不报 500，回退到单据默认语言。
- 某个非英文词典缺少键时回退英文，并由词典完整性测试阻止遗漏进入主分支。
- 历史英文和中文单据不迁移、不重写，继续按已保存语言输出。

### 7. 视觉与字体

Docker 当前存在支持西里尔字母和西班牙语字符的 DejaVu Sans 字体。打印字体栈加入明确的 DejaVu Sans 回退，避免俄语 PDF 出现方框。

俄语标签通常比英文更长，视觉检查必须覆盖：

- 右上角单据大标题
- 买方与商业信息面板
- 明细表头
- 汇总与条款区域
- PI 银行页
- 发票物流区域
- 装箱表格
- 页码与续页标题

允许标签正常换行，不允许覆盖数值、挤压表格列或破坏自动分页。

## 验收标准

1. 新建和编辑单据可保存四种默认语言。
2. 同一单据可通过打印页临时切换四种语言，且不修改数据库默认语言。
3. 五种单据的固定标签在四种语言下完整显示，不残留无意的英文硬编码。
4. 中文现有映射缺口全部补齐。
5. 产品、客户、条款、卖方和银行实际内容在切换语言前后逐字不变。
6. HTML 预览、Chrome 打印和 Download PDF 使用同一语言。
7. Excel 导出使用所选输出语言。
8. 非法语言不会造成 500，按规则回退。
9. 四套语言文件的键完全一致，并有自动测试验证。
10. 俄语和西班牙语 PDF 无乱码、溢出、重叠或异常分页。
11. 现有英文、中文和分页相关测试继续通过。

## 非目标

本阶段不实现：

- AI 自动翻译产品描述或商业条款
- 每个字段保存四份翻译内容
- 多语言单据副本或版本表
- 用户自定义语言和后台词典编辑器
- 自动翻译客户、国家、地址、银行和合同法律文本

如未来需要完整俄语或西班牙语合同，应单独设计“人工确认后的翻译内容版本”，不能把本阶段的标签本地化等同于法律文本翻译。

## 实施边界

- 不新增或修改数据库表。
- 不改变金额、分页算法和单据类型切换的业务规则。
- 不影响后台管理界面的全局语言。
- 不创建新的打印模板。
- 仅清理与单据多语言直接相关的重复词典和硬编码。
