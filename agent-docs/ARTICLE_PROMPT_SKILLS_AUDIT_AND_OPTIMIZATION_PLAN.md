# GEOFlow Article Prompt Skills Audit and Optimization Plan

> Status: review only; no prompt, database, generation-flow, or UI change has been applied.
>
> Audit date: 2026-07-20
>
> Execution detail: see [ARTICLE_PROMPT_SKILLS_IMPLEMENTATION_EXECUTION_PLAN.md](./ARTICLE_PROMPT_SKILLS_IMPLEMENTATION_EXECUTION_PLAN.md). The implementation plan incorporates parallel requirement, code, test, and risk reviews and supersedes the original phase order where they conflict.

## 1. Product objective

Improve the current article Skill Prompt system without turning it into another rigid template layer.

The optimized system should:

1. Let the Master Prompt own global truth, RAG, privacy, language, and output boundaries.
2. Let each Skill Prompt own only the decision logic unique to its article type.
3. Let runtime code inject title, keyword, knowledge context, target language, and final output constraints.
4. Let the optional Layout Skill handle post-generation layout enhancement instead of forcing rich layout into every article-generation prompt.
5. Preserve manual Skill selection and the explicit "no Skill" path.
6. Avoid changing historical tasks or regenerating existing articles automatically.

## 3. Critical system findings

### P0-1. Packaged presets and the live database are inconsistent

The live database contains seven Skills. `database/seeders/data/prompt_presets.php` packages only three Skills:

- GEO Skill - Comparison;
- GEO Skill - Buying Guide;
- GEO Skill - Use Case.

Those three packaged versions are already much shorter than their live database versions. Running `PromptPresetSeeder` can rename and overwrite the corresponding live records. Technical, Troubleshooting, Case Study, and Definition are not packaged and therefore cannot be restored consistently on a new installation.

Required decision for implementation:

- Treat packaged presets as the source of truth.
- Add all approved Skills to the preset file.
- Update the database through a controlled, backed-up synchronization command.
- Do not run the current Seeder against production data before the approved Skill contents are finalized.

### P0-2. Unsupported and duplicated prompt responsibilities

The current Master contains unsupported template variables such as `{{language}}`, `{{audience}}`, and `{{SkillPrompt}}`. Runtime only renders title, keyword, and knowledge variables. Runtime already concatenates Master, Skill, and optional Style, so `{{SkillPrompt}}` is unnecessary.

Required correction:

- Remove unsupported blocks from the Master.
- Keep Skill content variable-free unless a supported variable has a demonstrated need.
- Keep target-language enforcement in runtime.
- Add a test that generated prompts contain no unresolved built-in placeholders.

### P0-3. Every Skill encourages a duplicate H1

All current Skills include `# {{title}}`, while the article page already renders the article title.

Required correction:

- Runtime should state that the body must not output an H1.
- Skill examples must begin with body copy or H2.
- Existing articles must not be rewritten automatically.

### P0-4. Skill selection is task-level, while articles are title-level

A task stores one `skill_prompt_id`. If one title library contains mixed intents, every article generated by that task receives the same Skill. Current smart recommendation also scores the title library name and up to 60 title samples, then returns one Skill for the entire task.

Product risk:

- A comparison title and a how-to title in the same task can receive the same Buying Guide Skill.
- A dominant title pattern can hide minority intents in a mixed library.

Recommended boundary:

- Keep manual task-level Skill selection unchanged.
- Keep "no Skill" unchanged.
- For Auto mode only, resolve intent per selected title at generation time in a later phase.
- Record the actually resolved Skill on each article trace.

### P0-5. Generation traces do not preserve exact prompt versions

The article trace stores prompt IDs and names, but not content snapshots, version numbers, or hashes. Editing a Skill changes later generations without providing an exact historical explanation of which text produced an older article.

Recommended correction:

- Add a deterministic SHA-256 hash for Master, Skill, Style, and final composed prompt to the generation trace.
- Optionally store prompt version labels, but do not store full RAG context or sensitive prompt text in the UI.
- Show the version/hash only in the generation-source detail area.

## 4. Shared optimization contract for all Skills

### Keep in Master Prompt

- factual accuracy and no fabrication;
- source and RAG priority;
- distinction between verified facts, inference, and unknowns;
- privacy and customer-data protection;
- unsupported claim restrictions;
- global tone and anti-hype boundary;
- general GEO/SEO extractability principles;
- target reader baseline;
- relationship evidence rules shared by all Skills.

### Keep in runtime

- title;
- keyword;
- retrieved knowledge context;
- target language;
- Markdown body-only requirement;
- no unresolved placeholders;
- no body H1;
- current internal-link policy;
- Master -> Skill -> Style composition order.

### Keep in each Skill

- when the Skill applies;
- when it should not apply;
- unique reasoning sequence;
- unique evidence requirements;
- optional section menu;
- article-type-specific failure checks.

### Remove from every Skill

- repeated global RAG rules;
- repeated privacy boilerplate except Case/Troubleshooting-specific additions;
- repeated general audience lists;
- repeated general GEO/SEO instructions;
- repeated general writing-style instructions;
- repeated final output instructions already enforced by runtime;
- long sample heading templates that look mandatory;
- `# {{title}}`.

### Shared structure guardrails

These should be defaults, not mechanical scoring targets:

1. A typical 1,200-2,200 word article usually needs about 5-8 meaningful H2 sections.
2. Use H3 only when a parent section contains at least two genuine peer subtopics.
3. A section should normally contain at least two useful prose paragraphs or one meaningful table/list plus explanation.
4. Do not use `Quick Answer`, `Key Takeaways`, and `Introduction` together when they repeat the same point.
5. FAQ, checklist, comparison table, decision matrix, and summary table are conditional modules.
6. Do not create a heading for a single sentence.
7. Each section must add a new fact, distinction, decision criterion, procedure, risk, or example.
8. Layout richness is optional and should not override factual completeness.

## 5. Skill-by-Skill audit

### 5.1 Comparison & Evaluation

#### Valid product purpose

Helps a buyer compare alternatives and make a conditional choice. This Skill is necessary and should remain.

#### Current issues

- Repeats global factual, commercial, GEO, tone, and output rules.
- The long suggested structure encourages the same Quick Answer -> Takeaways -> Introduction -> Table -> Mistakes -> FAQ pattern.
- `A vs B`, alternatives, and multi-option comparisons are mixed without explaining structural differences.
- A comparison table is treated as almost universal even when evidence is asymmetric.
- "Which is better" may overlap with Buying Guide.

#### Keep

- fair comparison criteria;
- strengths, limits, trade-offs, and negative-fit scenarios;
- conditional recommendation;
- evidence-gap disclosure;
- option symmetry.

#### Add or clarify

1. Define comparison objects before judging them.
2. Use the same criteria for every option unless a difference is explicitly explained.
3. Do not score, rank, or declare a winner without comparable evidence.
4. Separate direct alternatives from products that solve different problems.
5. For more than two options, use grouped criteria rather than repeating full mini-essays.
6. If evidence is asymmetric, state what is known for each side instead of filling gaps by inference.
7. Route titles focused mainly on "how to choose" to Buying Guide unless direct alternatives are central.

#### Target size

350-550 English words.

#### Acceptance examples

- `Air-Cooled vs Water-Cooled Chillers` -> Comparison.
- `How to Choose a Chiller` -> Buying Guide, not Comparison.
- `Best Chiller for Battery Manufacturing` -> Buying Guide or Application depending on title focus and evidence.

### 5.2 Buying Guide & Selection

#### Valid product purpose

Turns buyer requirements into selection criteria and a verification checklist. This Skill is necessary and currently the most used for recent articles.

#### Current issues

- The longest active Skill used in recent generation.
- Fixed chain and recommended sections produce formulaic articles.
- Decision matrix, comparison, common mistakes, RFQ checklist, FAQ, and conclusion are all strongly implied.
- Required criteria and optional preferences are not consistently separated in the live version.
- Repeats Master claim discipline and GEO rules.

#### Keep

- buyer goal and constraints;
- must-have criteria;
- trade-offs;
- warning signs and mistakes;
- practical verification questions;
- next-step checklist.

#### Add or clarify

1. Separate requirements into must-have, context-dependent, and preference.
2. Distinguish selection criteria from supplier claims that require verification.
3. Include total-cost or maintenance considerations only when relevant and supported.
4. Do not force a comparison table when the article explains a single selection process.
5. Use a decision matrix only when multiple alternatives and enough evidence exist.
6. Avoid repeating selection advice in Key Takeaways, Factors, Mistakes, Checklist, and Conclusion.
7. End with information the buyer should prepare, not an aggressive sales CTA.

#### Target size

400-650 English words.

### 5.3 Industry Application & Solution

#### Valid product purpose

Connects an industry/process problem to suitable solution capabilities. This Skill is necessary.

#### Current issues

- "Industry", "application", "use case", and "solution page" are treated as one shape.
- It can drift into unsupported product promotion.
- It can overlap with Case Study when an example is presented as a real result.
- Generic claims such as "commonly used" can still be produced without evidence.
- The full section template is too prescriptive.

#### Keep

- application context;
- production pain point;
- technical requirements;
- solution fit;
- implementation constraints;
- negative-fit conditions;
- readiness checklist.

#### Add or clarify

1. Distinguish industry overview, process application, and specific solution-fit titles.
2. Start from the process requirement, not the product catalogue.
3. Use category-level solutions when no specific product evidence is available.
4. Do not describe a scenario as a real customer case unless Case data supports it.
5. Treat "commonly used", market adoption, and industry-wide behavior as claims requiring evidence or cautious qualification.
6. Explain unsuitable environments and prerequisite infrastructure where relevant.

#### Target size

400-650 English words.

### 5.4 Technical Explanation & Working Principle

#### Valid product purpose

Explains mechanisms, process steps, components, and performance factors. This Skill is necessary.

#### Current issues

- Strong overlap with Definition & Beginner Guide.
- Both list `What Is`, `Understanding`, and introductory titles as suitable.
- The component and parameter examples can encourage invention when source coverage is weak.
- It mixes concept explanation, component guide, and working-principle article into one large template.
- It may overproduce technical sections even when the title asks for a narrow explanation.

#### Keep

- mechanism or process flow;
- verified components;
- parameters that affect the mechanism;
- application boundaries;
- technical misconceptions when relevant.

#### Add or clarify

1. Use this Skill when the main question is "how/why does it work", not merely "what is it".
2. Require source support before naming internal components or parameter effects.
3. Separate mechanism facts from operational recommendations.
4. Use numbered process steps only when there is a real sequence.
5. Do not invent diagrams, equations, exact values, or pseudo-technical explanations.
6. If source knowledge supports only a definition, fall back to Definition Skill.

#### Target size

400-650 English words.

### 5.5 Troubleshooting & Maintenance

#### Valid product purpose

Provides symptom -> cause -> diagnosis -> corrective action -> prevention logic. This Skill is valuable for after-sales content but has higher safety risk.

#### Current issues

- No task has used it yet, so production behavior is unvalidated.
- "General industry principle" is a broad loophole that can permit unsupported causes or repairs.
- Operator-safe checks and technician-only actions are not separated strongly enough.
- A long generic symptom/cause/action template may imply certainty.
- The article may accidentally expose private after-sales cases.

#### Keep

- symptom-first diagnosis;
- multiple possible causes;
- first checks;
- corrective action and prevention;
- escalation conditions;
- maintenance intervals only when verified.

#### Add or clarify

1. Label causes as verified, likely, or possible based on evidence.
2. Separate safe operator checks from qualified-technician actions.
3. Do not provide instructions that bypass guards or involve unsafe electrical, pneumatic, pressure, heat, chemical, or moving-part work.
4. Require lockout, shutdown, depressurization, cooling, PPE, or supplier procedures when applicable, without inventing equipment-specific steps.
5. Do not claim a universal fix.
6. Request/describe diagnostic evidence: model, alarm, material, parameter, environment, timing, photos/video, and maintenance history.
7. Default to anonymized after-sales examples.
8. Do not convert unresolved support tickets into authoritative public guidance.

#### Target size

500-750 English words because safety boundaries are genuinely Skill-specific.

### 5.6 Case Study & Success Story

#### Valid product purpose

Transforms verified Case DB material into an evidence-based, privacy-safe application story. This Skill is necessary if Case DB is to contribute to public content.

#### Current issues

- No task has used it yet.
- "Case study", "success story", "application example", inquiry, and troubleshooting case are mixed.
- It requires case evidence but runtime does not visibly enforce a minimum Case source before the Skill is selected.
- There is no clear publication-consent field referenced by the Skill.
- It can overlap with Application Skill.

#### Keep

- strict no-fiction rule;
- privacy and anonymization;
- background -> requirement -> solution -> implementation -> result/lesson;
- no invented metrics or testimonials;
- evidence-limited scenario fallback.

#### Add or clarify

1. Define four evidence states:
   - completed case with verified result;
   - implementation case without final result;
   - inquiry/application scenario;
   - after-sales lesson.
2. Only call content a "success story" when completion and result evidence exist.
3. If no Case source is retrieved, block automatic Case Study use or downgrade to Application analysis.
4. Default to anonymized identities unless explicit publication permission exists.
5. Do not infer customer country, industry, production volume, ROI, or satisfaction.
6. Distinguish actual result, customer statement, and internal sales assessment.
7. Avoid turning CRM opportunity probability or sales notes into public outcome claims.

#### Target size

500-750 English words because evidence-state and privacy logic are Skill-specific.

### 5.7 Definition & Beginner Guide

#### Valid product purpose

Explains terminology and basic decision context for early-stage readers. This Skill is useful, but its boundary with Technical Explanation must be tightened.

#### Current issues

- No task has used it yet.
- Overlaps heavily with Technical Explanation title patterns.
- The long template can make a simple definition article unnecessarily large.
- It can still drift into buying-guide advice.
- "Everything beginners should know" can encourage unsupported breadth.

#### Keep

- plain definition;
- basic purpose and place in workflow;
- common types/related terms;
- beginner misunderstandings;
- signals that deeper evaluation is needed.

#### Add or clarify

1. Use when the primary intent is orientation, terminology, or basic scope.
2. Route mechanism-heavy titles to Technical Explanation.
3. Route selection-heavy titles to Buying Guide.
4. Explain jargon on first use and avoid unnecessary component-level depth.
5. Keep the article concise when the concept is narrow.
6. Do not force tables, FAQs, or advanced parameters.

#### Target size

300-500 English words.

## 6. Intent boundaries and routing matrix

| Primary reader question | Recommended Skill |
|---|---|
| What is this, and where does it fit? | Definition |
| How or why does it work? | Technical Explanation |
| Which of these alternatives fits my conditions? | Comparison |
| What criteria should I use to choose/configure/buy? | Buying Guide |
| How does this solve a specific industry or process problem? | Application |
| Why is this problem happening and what should be checked? | Troubleshooting |
| What happened in a verified real project or field case? | Case Study |

Tie-break rules:

1. Use the title's primary promised outcome, not individual keywords alone.
2. `What is` -> Definition unless the title explicitly asks how it works.
3. `A vs B` -> Comparison even if the conclusion contains buying advice.
4. `How to choose` -> Buying Guide even if alternatives are compared inside.
5. `[solution] for [industry]` -> Application unless a verified customer/project is named as the central evidence.
6. `Why/fix/troubleshoot` -> Troubleshooting.
7. `Case study/customer project/field result` -> Case Study only with retrievable Case evidence.

## 7. Smart recommendation audit

### Current capability

The rules engine recognizes only:

- comparison;
- buying guide;
- application.

It does not automatically recommend Technical, Troubleshooting, Case Study, or Definition.

### Current risks

- The broad Application regex includes words such as industry, manufacturing, process, and case, which can absorb Technical or Case titles.
- The library-level score combines many titles and can hide mixed intent.
- Matching a Skill by searching aliases in its name and full content is fragile after prompt renaming.
- There is no stable machine-readable intent field on Prompt records.

### Recommended evolution

#### Phase A: low-risk rules improvement

1. Add a stable intent identifier separate from the display name, for example `comparison`, `buying_guide`, `application`, `technical`, `troubleshooting`, `case_study`, `definition`.
2. Match by intent identifier, never by scanning prompt prose.
3. Add patterns for the four missing intents.
4. Introduce tie-break and minimum-confidence rules.
5. Show the matched intent and confidence, preserving manual override.

#### Phase B: per-title Auto mode

1. Keep task-level manual Skill behavior unchanged.
2. When Auto is selected, classify each picked title during generation.
3. Use the selected title's intent, not the whole library majority.
4. If confidence is low, generate with Master only or use the manually configured fallback.
5. Record the resolved Skill and reason in the article generation trace.

AI classification is not required for the first implementation. Deterministic rules plus manual override are sufficient initially.

## 8. Prompt governance improvements

### Required

1. Make packaged presets the version-controlled source of truth.
2. Package all seven approved Skills.
3. Add a preview/diff command before synchronizing presets into a live database.
4. Back up the `prompts` table before bulk synchronization.
5. Preserve prompt IDs used by existing tasks where possible.
6. Add prompt content hashes to generation traces.
7. Establish names such as `GEO Skill - Comparison v2` only if the system adopts explicit version records; otherwise keep stable names and trace hashes.

### Recommended later

1. Add `intent_key`, `is_system`, and `is_enabled` fields.
2. Prevent disabled Skills from appearing in new-task selection while preserving historical references.
3. Add a read-only preview showing Master + Skill + Style boundaries and estimated size.
4. Add "duplicate Skill" instead of encouraging direct edits to packaged system presets.

## 9. Implementation sequence for approval

### Phase 1 - correctness and backup

- Export current prompt records.
- Add tests for unresolved variables and no body H1.
- Remove unsupported Master variables.
- Add prompt hashes to generation trace.
- Do not change Skill wording yet.

### Phase 2 - shared contract and seven Skill rewrites

- Finalize the slim Master boundary.
- Rewrite all seven Skills using the per-Skill requirements above.
- Target combined Master + Skill size of roughly 1,300-1,900 words before RAG context.
- Preserve Case and Troubleshooting safety/privacy details even if they remain slightly longer.

### Phase 3 - preset synchronization

- Put all approved prompt contents in `prompt_presets.php`.
- Add preview/diff and idempotency tests.
- Synchronize the local database only after preview approval.
- Verify existing task references still point to the intended records.

### Phase 4 - routing improvement

- Add stable intent keys.
- Support all seven intents in deterministic recommendation.
- Improve tie-break rules.
- Keep manual and no-Skill choices.

### Phase 5 - per-title Auto mode

- Resolve Skill per generated title only when task selection is Auto.
- Record the resolved Skill and confidence per article.
- Keep manually selected task-level Skill unchanged.

### Phase 6 - evaluation

Use at least two titles per Skill, including one ambiguous boundary title.

Evaluate:

- factual support and evidence gaps;
- correct Skill routing;
- title/section density;
- repeated opening/summary sections;
- buyer usefulness;
- negative-fit and uncertainty handling;
- language consistency;
- prompt token size;
- Case privacy and Troubleshooting safety;
- output differences between Master-only and Master + Skill.

Do not approve based only on whether the model generated valid Markdown.

## 10. Minimum test checklist

1. Master + Skill + Style composition order remains stable.
2. No built-in placeholder remains unresolved.
3. Target language instruction wins over prompt language.
4. Article body does not require an H1.
5. Manual Skill selection remains unchanged.
6. No-Skill path remains unchanged.
7. Auto mode handles all supported intents and low-confidence fallback.
8. Mixed title libraries do not force one Auto Skill on every article after Phase 5.
9. Seeder preview reports create/update/rename/unchanged actions.
10. Seeder remains idempotent.
11. Existing task foreign keys remain valid.
12. Generation trace records prompt identity and hashes.
13. Case Skill refuses or downgrades when no Case evidence exists.
14. Troubleshooting output contains safe escalation boundaries.
15. Recent representative articles show lower heading repetition without losing information coverage.

## 11. PM recommendation

Recommended approval scope:

- Approve Phases 1-3 as the first controlled delivery.
- Approve Phase 4 only after the seven intent definitions are accepted.
- Treat Phase 5 as a separate workflow enhancement because it changes Auto mode from task-level to article-level behavior.
- Execute Phase 6 after every content/routing phase, not only at the end.

The highest-value change is not adding more instructions. It is reducing duplicated instructions, making intent boundaries explicit, and ensuring the database, packaged presets, and actual generation trace describe the same system.
